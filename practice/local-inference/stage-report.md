## 环境与验收

- Windows 11，RTX 5070，驱动 `610.88`。Ollama `0.40.17`，`qwen3:8b`，模型 ID `500a1f067a9f`。三轮复验记录了相同的完整模型摘要和 `Q4_K_M` 量化，模型显存计数均为 `5584495574` 字节。[三轮运行清单](results/concurrency-recheck/manifest.json)

- 每次独立启动先用 4 条请求预热，然后执行 4 组配对。每个条件每组发送 2 条短提示和 2 条长提示，输入分别为 51 和 750 token。不同请求使用不同的数字开头，正式请求实际只复用 3–5 个前缀 token。
- 每条回复须通过 HTTP 200、目标文本和 `done_reason: stop` 检查。正式请求每条生成 20 token，各轮实际峰值在途数与设定一致。吞吐用整轮输出 token 总数除以墙钟时间，延迟从每条请求发出开始计时。预热记录保留在原始文件中。

## 阶段结论

普通 HTTP 和流式读取均已验收。单并发基线表明长提示的前缀大量命中时，客户端更快收到首段正文。低缓存的短长混合负载下，并发 2 在四次运行中持续提高整轮吞吐，同时增加单条延迟。延迟优先的调用可用并发 1 作为当前对照，批量吞吐优先的调用可用并发 2 作为当前对照。

复验只覆盖同一台机器、两个服务端槽和固定的短输出。随后完成 64 条等长输入对照，比较 20 与 117 token 输出下的并发收益。[长输出逐次结果](results/2026-11-23-output-length.json)

之后固定两个槽，用 117 token 输出跑完 96 条请求。并发 2 和 4 的吞吐中位数分别为 162.19 和 163.58 token/s，首段正文 P90 分别为 282.15 和 1706.02 ms。[并发 2 与 4 逐次结果](results/2026-11-23-queue.json)
