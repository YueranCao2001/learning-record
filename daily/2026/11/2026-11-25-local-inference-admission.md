# 2026-11-25：本地推理实作：突发到达下的有限队列与放行预算

## 今日目标

**实测结论** — 当前双槽配置下，限制为一条等待并设 1 秒放行预算，成功回复的端到端 P90 从 2.89 秒降到 1.46 秒，完整回复从 80/80 降到 40/80。拆分后看到，只设预算与组合策略完成数相同，队列上限主要把一部分等待超时提前为立即拒绝。该配置作为过载保护的实验档，完成率与延迟一起评估。

验证客户端限制排队后，一个固定的突发批次会完成、超时和拒绝多少条。当两条在途请求都在生成时，昨天批内后两条的排队中位数约为 1.47 秒。今天固定输入和到达形态，比较原有等待方式与一条等待、1000 ms 放行预算的组合策略。每种策略各跑两轮，逐条核对终态和 HTTP 开始时间。[昨日实测与参数依据](2026-11-24-local-inference-capacity.md)

## 核心概念

等待预算从实际提交起算。客户端处理新提交或发放名额前先清理到期等待，HTTP 调用前再用单调时钟核对 `http_start_ms < deadline_ms`。达到截止时间的请求走放行前超时，等待容量已满时到达的请求走队列满拒绝。两类结果的 HTTP 开始时间均为空。

完成率以全部提交为分母，端到端 P90 只统计完整回复并标出样本数。排空时间从最后一次实际提交算到整轮最后一个终态。策略改变哪些请求进入成功样本，所以完成率与成功 P90 一起解读。

## 示例与练习

### 配置与复现

沿用本机 RTX 5070、Ollama `0.40.17` 和 `qwen3:8b`，双槽、每槽上下文 2048、最多两条在途。每 3.2 秒提交四条，共十批、每轮 40 条，短长输入交替为 190 和 889 token，目标回复为 117 token。每种策略两轮，第二轮反转顺序，同一实例内使用不同标签降低前缀复用。组合策略最多一条等待，放行预算为 1000 ms。[复现入口](../../../practice/local-inference/README.md#验证突发到达时的有限等待队列)

```powershell
python .\admission_probe.py --output .\bounded-admission-result.json
```

合成检查把 HTTP 调用时钟固定在截止点和截止前 1 ms，分别确认超时且未发出 HTTP、以及允许放行。另在四条同时提交的短测试中持有两个名额，核对两条完成、一条等待到期和一条队列满拒绝。下面的策略对照由真实模型运行。[逐次结果](../../../practice/local-inference/results/2026-11-25-bounded-admission.json)

### 实测对照

| 策略 | 完整回复 / 提交 | 放行前超时 | 队列满拒绝 | 其他错误 | 成功回复端到端 P90 | 排空时间中位数 |

两轮基线各完成 40 条，两轮保护组各得到 20 条完整回复、10 条等待超时和 10 条拒绝。两组实测 HTTP 在途峰值均为 2，等待队列峰值从 2 降为 1。四轮提交相对计划的最大偏差为 15.29 ms。已放行请求均通过正文和停止标记验收。40 条未放行记录的 HTTP 开始时间均为空。

第一轮保护组的首批可以按 `request_id` 核对。`640` 和 `641` 分别在约 1432 和 1421 ms 完成。`642` 等待约 1001 ms 后退出，`643` 提交时队列已满，立即结束。放行预算作用到 HTTP 开始之前，所以前两条的完整耗时可以超过 1 秒。[该批及完整终态](../../../practice/local-inference/results/2026-11-25-bounded-admission.json)

### 拆开测试队列上限和等待预算

组合对照同时改动两个变量。补测增加「只限等待队列为一条」和「只设 1000 ms 放行预算」，并在同一个新实例里重跑两个参照组。每轮五批、20 条，仍然每 3.2 秒提交四条，沿用相同短长输入比例、模型和两条在途上限。四种策略各跑两轮，第二轮反转顺序。按批内位置和输入长度核对成功样本，另验收超时与拒绝的终态。[运行命令](../../../practice/local-inference/README.md#验证突发到达时的有限等待队列)

| 策略 | 完整回复 / 提交 | 放行前超时 | 队列满拒绝 | 全部成功回复 P90 | 批内前两条 P90，均为 20 条 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 基线 | 40/40 | 0 | 0 | 2897.88 ms | 1461.71 ms |
| 只限一条等待 | 30/40 | 0 | 10 | 2568.22 ms | 1429.97 ms |
| 只设 1 秒预算 | 20/40 | 20 | 0 | 1437.64 ms | 1437.64 ms |
| 同时启用 | 20/40 | 10 | 10 | 1458.13 ms | 1458.13 ms |

只限一条等待时，批内第四条全部被拒绝，第三条继续等待并完成。由于本次输入按短、长、短、长排列，该组完成了 20 条短输入和 10 条长输入。只设预算时，第三、第四条都等到超时。组合策略仍完成 20 条，其中 10 条原本要等到超时的第四条改为提交时直接拒绝。

各组批内前两条均为一短一长，20 条全部完成，P90 聚在 1429.97–1461.71 ms。整体成功 P90 的差距主要来自后两条是否进入成功样本。补测 160 条均得到唯一终态，HTTP 在途峰值为 2，设定队列上限的组等待峰值为 1。两种带预算的组，超时终态比逻辑截止时间的中位延后分别为 9.17 和 10.94 ms，超时请求的 HTTP 开始时间均为空。[拆分策略逐次结果](../../../practice/local-inference/results/2026-11-25-admission-breakdown.json)

## 遇到的问题

报告成功 P90 时要带分母和样本构成。只限队列后长输入只完成一半，加入预算后两条批内尾部请求都在 HTTP 前结束。这些差异依赖短长输入顺序、四条突发和两条在途上限。流量回落后的恢复还需要单独按时间段观察。

## 今日总结

今天两组实验共验收 320 条提交，每条均有唯一终态。就这条突发轨迹而言，等待预算决定哪些排队请求还会进入执行，队列上限决定其中多少条能更早返回拒绝。周四保留组合策略作为过载对照，验证流量回落后能否恢复完成率。
