# 2026-11-24：本地推理实作：缩小可持续到达速率范围

**当前容量判断** — 对这台机器上的双槽配置和固定短长混合负载，**均匀到达的 1.25 条/s 可以作为低等待对照**。同样的平均速率改成每批四条，客户端排队 P90 升到 1.48 秒。均匀到达时，1.375 条/s 已出现跨半程的等待增长，升到 1.50 条/s 后增长主要发生在 HTTP 发出前。今天共跑 14 轮，552 条回复全部通过。

昨天的 1 和 2 条/s 已经拉开差距。今天先将均匀流量的观测范围缩小到 1.25–1.50 条/s，再测中间档和等时长窗口。最后固定平均速率，对照均匀提交和成批提交。验收时逐轮核对实际到达、客户端排队、窗口内完成量及回复完整性。[昨日对照](2026-11-23-local-inference-http-smoke.md)

## 核心概念

提交时钟独立于回复。两个工作线程都忙时，后续请求会在客户端等待。排查时用以下三个时间戳定位耗时。

| 指标 | 计算口径 |
| --- | --- |
| 放行前等待 | `start_ms - submitted_ms`，从实际提交到开始 HTTP |
| HTTP 阶段耗时 | `end_ms - start_ms`，从开始 HTTP 到客户端读完并校验回复 |
| 端到端耗时 | `end_ms - submitted_ms`，从实际提交到回复验收结束 |

`already_waiting_at_arrival` 只数新请求到达时已提交、还未开始 HTTP 的此前请求。末次提交后的未完成数同时包括在途和等待。分位数按请求排序取最近秩，16 条取第 15 个值，24 条取第 22 个值。端到端 P90 用逐条总耗时计算。

### 等待增加在哪一段

下表合并相同速率的两轮。每个半程有 32 条请求，统计各段均值。

| 到达速率 | 半程 | 放行前平均等待 | 开始 HTTP 至回复结束平均耗时 |
| ---: | --- | ---: | ---: |
| 1.25 条/s | 前 | 5.32 ms | 1436.77 ms |
| 1.25 条/s | 后 | 5.34 ms | 1436.99 ms |
| 1.50 条/s | 前 | 387.33 ms | 1450.60 ms |
| 1.50 条/s | 后 | 1490.93 ms | 1463.98 ms |

每秒 1.50 条时，后半程的放行前平均等待增加约 1104 ms，HTTP 阶段只增加约 13 ms。只从 HTTP 开始计时会漏掉这轮长负载的大部分延迟增长。周三的过载对照将从提交时刻开始计等待预算。

### 等时长补测

前两组的提交窗口长度不同。补测将两档都安排在 32 秒计划窗口内，前后半程各 16 秒。每轮分别提交 40 和 44 条，短、长输入各占一半，使用相同模型摘要、并行配置和输出校验。各跑两轮，第二轮反转顺序。[等时长逐次记录](../../../practice/local-inference/results/2026-11-24-capacity-equal-window.json)

| 速率 | 轮次 | 前半程排队 P90 | 后半程排队 P90 | 末次提交后未完成 | 从末次提交到全部完成 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1.25 条/s | 1 | 7.11 ms | 6.81 ms | 2 | 1.32 秒 |
| 1.25 条/s | 2 | 7.06 ms | 7.05 ms | 2 | 1.38 秒 |
| 1.375 条/s | 1 | 7.31 ms | 116.92 ms | 3 | 1.48 秒 |
| 1.375 条/s | 2 | 48.13 ms | 214.81 ms | 3 | 1.61 秒 |

168 条回复全部通过。两档在新请求到达时都没有此前已提交仍在等待的请求，但 1.375 条/s 的后半程 P90 两轮均上升，末次提交后也都多剩一条请求。这个方向与先前 48 条补测一致，幅度有波动：同档后半程 P90 先前为 502–690 ms，这次为 117–215 ms。做后续过载对照时应保留逐轮数据。

### 平均速率相同时，突发到达会怎样

两组都在 32 秒内提交 40 条，平均每秒 1.25 条。均匀组每 0.8 秒提交一条，批量组每 3.2 秒提交四条。每轮都是 20 条短输入和 20 条长输入，输出校验和在途上限相同，第二轮反转组别顺序。平均速率以固定窗口内的实际提交数除以 32 秒计算，窗口结束时的完成数按固定时点统计。[到达形态逐次结果](../../../practice/local-inference/results/2026-11-24-arrival-shape.json)

| 到达形态 | 完整回复 | 排队 P90 | 端到端 P90 | 32 秒内完成，每轮 |
| --- | ---: | ---: | ---: | ---: |
| 均匀 | 80/80 | 7.24 ms | 1.48 秒 | 39/40 |
| 每批四条 | 80/80 | 1482.70 ms | 2.94 秒 | 40/40 |

批量组按每批提交顺序拆开看，前两条的等待中位数是 9.66 ms，后两条是 1468.32 ms。以第一轮第二批为例，四条都在 3.20 秒附近提交，前两条约在 3.21 秒开始 HTTP，后两条分别在 4.65 和 4.67 秒开始。两个名额被前两条占用时，后两条等了约一条推理请求的耗时。

两轮批量实验中，可与下一批对照的 18 批都提前处理完，领先下一批约 218–299 ms。批量组的最后一批约在 28.8 秒提交，均匀组的最后一条约在 31.2 秒提交，固定窗口的完成数也反映这段不同的排空时间。**窗口内可以处理完所有请求，批内仍可能出现显著的等待。**

## 遇到的问题

全部回复通过只能验收输出，容量判断看等待是否随提交窗口增长。最初两轮的 1.375 和 1.50 条/s，把排空计入吞吐后，整轮完成速率均约 1.32–1.33 条/s。今天的提交窗口约为 21–34 秒，当前范围适用于这台机器、这套输入混合和两条在途上限。长期容量仍需更长的到达窗口验证。

## 今日总结

把均匀到达的 1.25 条/s 留作低等待基线，1.50 条/s 留作持续积压对照。每批四条的轨迹可以稳定制造批内等待，适合作为下一轮队列容量和等待预算的对照输入。
