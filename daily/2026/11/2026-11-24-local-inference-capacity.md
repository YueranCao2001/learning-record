## 今日目标

**当前容量判断** — 对这台机器上的双槽配置和固定短长混合负载，**1.25 条/s 可以作为低等待对照，1.375 条/s 已观察到跨半程的等待增长**。继续升到 1.50 条/s，主要增加的是 HTTP 发出前的排队。今天三个速率共跑 6 轮，224 条回复全部通过。

昨天的 1 和 2 条/s 已经拉开差距。今天要把观测范围缩小，因此保持负载和并行配置，测 1.25、1.50 条/s，再加测中间档。每档验收两轮的实际到达速率、前后半程排队、末次提交后未完成量和回复完整性。[昨日对照](2026-11-23-local-inference-http-smoke.md)

## 核心概念

提交时钟独立于回复。两个工作线程都忙时，后续请求会在客户端等待。排查时用以下三个时间戳定位耗时。

| 指标 | 计算口径 |
| --- | --- |
| 放行前等待 | `start_ms - submitted_ms`，从实际提交到开始 HTTP |
| HTTP 阶段耗时 | `end_ms - start_ms`，从开始 HTTP 到客户端读完并校验回复 |
| 端到端耗时 | `end_ms - submitted_ms`，从实际提交到回复验收结束 |

`already_waiting_at_arrival` 只数新请求到达时已提交、还未开始 HTTP 的此前请求。末次提交后的未完成数同时包括在途和等待。分位数按请求排序取最近秩，16 条取第 15 个值，24 条取第 22 个值。端到端 P90 用逐条总耗时计算。

### 等待增加在哪一段

下表合并相同速率的两轮。每个半程有 32 条请求，统计各段均值。

| 到达速率 | 半程 | 放行前平均等待 | 开始 HTTP 至回复结束平均耗时 |
| ---: | --- | ---: | ---: |
| 1.25 条/s | 前 | 5.32 ms | 1436.77 ms |
| 1.25 条/s | 后 | 5.34 ms | 1436.99 ms |
| 1.50 条/s | 前 | 387.33 ms | 1450.60 ms |
| 1.50 条/s | 后 | 1490.93 ms | 1463.98 ms |

每秒 1.50 条时，后半程的放行前平均等待增加约 1104 ms，HTTP 阶段只增加约 13 ms。只从 HTTP 开始计时会漏掉这轮长负载的大部分延迟增长。周三的过载对照将从提交时刻开始计等待预算。

## 遇到的问题

全部回复通过只能验收输出，容量判断看等待是否随提交窗口增长。把停止提交后的排空计入吞吐，1.375 和 1.50 条/s 两档的整轮完成速率均为约 1.32–1.33 条/s。三档提交窗口约为 21–34 秒，当前范围适用于这台机器、这套输入混合和两条在途上限。长期容量仍需更长的到达窗口验证。

## 今日总结

把 1.25 条/s 留作低等待基线，把 1.50 条/s 留作可重复触发积压的工况。中间档已经出现放行等待，容量复测优先拉长这一档的窗口。
