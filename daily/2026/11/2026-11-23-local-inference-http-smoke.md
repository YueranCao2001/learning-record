# 2026-11-23：本地推理实作：跑通第一条 HTTP 回复

## 今日目标

启动新的本地大模型推理服务与压测项目。先验证普通和流式 HTTP 请求能否返回可验收的完整回复，再建立单并发基线。基线完成条件是用短、长提示分别复现低缓存与高缓存请求，验证服务端实际缓存计数，并保留逐次延迟和生成吞吐。[练习入口](../../../practice/local-inference/README.md)

## 核心概念

- `/api/version` 成功说明 HTTP 服务已启动。第一次 `/api/chat` 还要加载模型并完成生成，才能验证整条推理链路。
- `stream: false` 一次性返回完整 JSON。`stream: true` 逐行返回 NDJSON，客户端拼接每个 `message.content`，收到 `done: true` 后验收整段回复。计时从客户端发送请求开始，首段正文取第一条含非空白正文的事件。一个事件可以包含多个 token，因此这里测的是客户端可见的首段时间。[Ollama 流式响应文档](https://docs.ollama.com/api/streaming)

## 示例与练习

在 Windows 11 和 RTX 5070 上启动独立进程，监听 `127.0.0.1:11435`。使用本机缓存的 `qwen3:8b`，设置单路并行、上下文 2048、温度为 0、最多生成 32 token。关闭思考输出，请求 `What is 2 + 2? Reply with just the number.`。[验证脚本](../../../practice/local-inference/smoke.ps1)

### 流式与普通请求的配对对照

使用同一服务版本、模型和 GPU。改为要求逐字复制 12 个固定英文单词，生成上限设为 64。先做一次不计入统计的预热，再串行发送 5 对请求。每对使用相同请求体，切换 `stream`，交替先后顺序。10 次均返回 HTTP 200、完整目标文本和正常停止。每个流式回复包含 20 条 NDJSON 事件，其中 19 条带正文。[客户端](../../../practice/local-inference/stream_probe.py) · [逐次结果](../../../practice/local-inference/results/2026-11-23-stream.json)

| 客户端指标 | 中位数 | 范围 |
| --- | ---: | ---: |
| 流式首段正文 | 26.02 ms | 13.18–32.15 ms |
| 流式完整回复 | 196.16 ms | 183.01–204.37 ms |
| 普通完整回复 | 198.01 ms | 183.90–209.22 ms |

用合成事件核验了思考内容和空白片段的计时处理、终止事件自带正文、流式提前断开和服务器错误。

### 单并发基线：提示长度与前缀缓存

保持 Ollama `0.40.17`、Qwen3 8B、RTX 5070、单路并行与上下文 2048。先发送一条独立预热请求，然后短、长提示分别执行 6 对，每对首发使用新开头，随即原样重发。长提示在同一个复制任务前增加 16 段固定背景文本。每对输入 token 数相同。24 次均返回完整目标文本并正常停止，每次服务端计数为 20 个生成 token。[基线脚本](../../../practice/local-inference/baseline_probe.py) · [逐次结果](../../../practice/local-inference/results/2026-11-23-baseline.json)

| 条件（每组 6 次） | 提示 token | 缓存 token | 首段正文中位数 | 完整回复中位数 | 服务端提示处理 / 生成速率中位数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 短提示，新开头 | 50–51 | 3 | 44.77 ms | 218.44 ms | 17.85 ms / 115.48 token/s |
| 短提示，原样重发 | 50–51 | 49–50 | 14.07 ms | 184.70 ms | 9.27 ms / 117.07 token/s |
| 长提示，新开头 | 748–750 | 3 | 171.29 ms | 348.78 ms | 145.90 ms / 112.74 token/s |
| 长提示，原样重发 | 748–750 | 747–749 | 18.78 ms | 194.32 ms | 9.42 ms / 114.94 token/s |

独立预热请求的首段正文耗时 1.56 秒，服务端模型加载耗时 1.46 秒。这条请求单独存档，四组统计只使用模型常驻后的 24 次请求。生成速率按每次请求的服务端生成 token 数除以生成耗时计算，后续并发对照还要按整轮墙钟时间统计总吞吐。

## 遇到的问题

原计划使用独立 llama.cpp Windows 包和 Qwen3-0.6B GGUF。官方运行包未能及时下载，Hugging Face GGUF 下载连接超时。检查时发现 Ollama 已安装且有 `qwen3:8b` 缓存，因此首日用这套组合完成同一个本机 HTTP 验证。后续性能对照需要固定服务实现、模型和运行配置。

流式对照的预热请求耗时 3.99 秒，服务端报告加载耗时 3.67 秒。后续重复提示都复用了 47 个 token 中的 46 个。单并发基线改用新开头和原样重发来分组，首发仍有 3 个公共模板 token 命中。重发固定发生在首发之后，因此结果适用于紧邻重复请求的场景。

## 今日总结

完成普通 HTTP 回复、流式拼接和单并发基线。长提示的首段正文中位数在原样重发时从 171.29 ms 降至 18.78 ms，服务端提示处理耗时同步下降。四组的单请求生成速率集中在约 113–117 token/s。
