# 2026-11-23：本地推理实作：跑通第一条 HTTP 回复

## 今日目标

启动新的本地大模型推理服务与压测项目。今天验证本机服务能否通过 HTTP 返回可验收的完整回复。完成条件是普通请求收到 HTTP 200、正文 `4` 和正常停止标记，随后用流式客户端拼接同一段固定文本，分别记录首段正文和结束时间，并保留逐次响应证据。[练习入口](../../../practice/local-inference/README.md)

## 核心概念

- `/api/version` 成功说明 HTTP 服务已启动。第一次 `/api/chat` 还要加载模型并完成生成，才能验证整条推理链路。
- `stream: false` 一次性返回完整 JSON。`stream: true` 逐行返回 NDJSON，客户端拼接每个 `message.content`，收到 `done: true` 后验收整段回复。计时从客户端发送请求开始，首段正文取第一条含非空白正文的事件。一个事件可以包含多个 token，因此这里测的是客户端可见的首段时间。[Ollama 流式响应文档](https://docs.ollama.com/api/streaming)

## 示例与练习

在 Windows 11 和 RTX 5070 上启动独立进程，监听 `127.0.0.1:11435`。使用本机缓存的 `qwen3:8b`，设置单路并行、上下文 2048、温度为 0、最多生成 32 token。关闭思考输出，请求 `What is 2 + 2? Reply with just the number.`。[验证脚本](../../../practice/local-inference/smoke.ps1)

### 流式与普通请求的配对对照

使用同一服务版本、模型和 GPU。改为要求逐字复制 12 个固定英文单词，生成上限设为 64。先做一次不计入统计的预热，再串行发送 5 对请求。每对使用相同请求体，切换 `stream`，交替先后顺序。10 次均返回 HTTP 200、完整目标文本和正常停止。每个流式回复包含 20 条 NDJSON 事件，其中 19 条带正文。[客户端](../../../practice/local-inference/stream_probe.py) · [逐次结果](../../../practice/local-inference/results/2026-11-23-stream.json)

| 客户端指标 | 中位数 | 范围 |

用合成事件核验了思考内容和空白片段的计时处理、终止事件自带正文、流式提前断开和服务器错误。

## 遇到的问题

原计划使用独立 llama.cpp Windows 包和 Qwen3-0.6B GGUF。官方运行包未能及时下载，Hugging Face GGUF 下载连接超时。检查时发现 Ollama 已安装且有 `qwen3:8b` 缓存，因此首日用这套组合完成同一个本机 HTTP 验证。后续性能对照需要固定服务实现、模型和运行配置。

预热的普通请求耗时 3.99 秒，服务端报告加载耗时 3.67 秒。后续 10 次请求都复用了 47 个提示 token 中的 46 个。首段时间依赖这次的模型常驻和前缀缓存条件，正式基线需要分别记录前缀命中和未命中的请求。

## 今日总结

完成普通 HTTP 回复和流式拼接验收。对固定文本和热前缀，流式模式在整段生成结束前就交付了首段正文，两种模式的完整回复耗时相近。当前结果只覆盖单并发和一个短提示。
