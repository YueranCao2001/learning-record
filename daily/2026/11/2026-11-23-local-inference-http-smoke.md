# 2026-11-23：本地推理实作：跑通第一条 HTTP 回复

## 今日目标

本地大模型推理服务与压测。先验收普通和流式 HTTP 回复，再建立短、长提示的单并发基线，并回答并发从 1 提到 2 后，吞吐和单条延迟如何变化。并发对照固定请求数、提示长度和验收规则，记录实际在途数、缓存命中、延迟、吞吐及失败，最后从新服务实例复跑检查结果方向。[练习入口](../../../practice/local-inference/README.md)

## 核心概念

- `/api/version` 成功说明 HTTP 服务已启动。第一次 `/api/chat` 还要加载模型并完成生成，才能验证整条推理链路。
- `stream: false` 一次性返回完整 JSON。`stream: true` 逐行返回 NDJSON，客户端拼接每个 `message.content`，收到 `done: true` 后验收整段回复。计时从客户端发送请求开始，首段正文取第一条含非空白正文的事件。一个事件可以包含多个 token，因此这里测的是客户端可见的首段时间。[Ollama 流式响应文档](https://docs.ollama.com/api/streaming)

## 示例与练习

在 Windows 11 和 RTX 5070 上启动独立进程，监听 `127.0.0.1:11435`。使用本机缓存的 `qwen3:8b`，设置单路并行、上下文 2048、温度为 0、最多生成 32 token。关闭思考输出，请求 `What is 2 + 2? Reply with just the number.`。[验证脚本](../../../practice/local-inference/smoke.ps1)

### 流式与普通请求的配对对照

使用同一服务版本、模型和 GPU。改为要求逐字复制 12 个固定英文单词，生成上限设为 64。先做一次不计入统计的预热，再串行发送 5 对请求。每对使用相同请求体，切换 `stream`，交替先后顺序。10 次均返回 HTTP 200、完整目标文本和正常停止。每个流式回复包含 20 条 NDJSON 事件，其中 19 条带正文。[客户端](../../../practice/local-inference/stream_probe.py) · [逐次结果](../../../practice/local-inference/results/2026-11-23-stream.json)

| 客户端指标 | 中位数 | 范围 |
| --- | ---: | ---: |
| 流式首段正文 | 26.02 ms | 13.18–32.15 ms |
| 流式完整回复 | 196.16 ms | 183.01–204.37 ms |
| 普通完整回复 | 198.01 ms | 183.90–209.22 ms |

用合成事件核验了思考内容和空白片段的计时处理、终止事件自带正文、流式提前断开和服务器错误。

### 单并发基线：提示长度与前缀缓存

保持 Ollama `0.40.17`、Qwen3 8B、RTX 5070、单路并行与上下文 2048。先发送一条独立预热请求，然后短、长提示分别执行 6 对，每对首发使用新开头，随即原样重发。长提示在同一个复制任务前增加 16 段固定背景文本。每对输入 token 数相同。24 次均返回完整目标文本并正常停止，每次服务端计数为 20 个生成 token。[基线脚本](../../../practice/local-inference/baseline_probe.py) · [逐次结果](../../../practice/local-inference/results/2026-11-23-baseline.json)

| 条件（每组 6 次） | 提示 token | 缓存 token | 首段正文中位数 | 完整回复中位数 | 服务端提示处理 / 生成速率中位数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 短提示，新开头 | 50–51 | 3 | 44.77 ms | 218.44 ms | 17.85 ms / 115.48 token/s |
| 短提示，原样重发 | 50–51 | 49–50 | 14.07 ms | 184.70 ms | 9.27 ms / 117.07 token/s |
| 长提示，新开头 | 748–750 | 3 | 171.29 ms | 348.78 ms | 145.90 ms / 112.74 token/s |
| 长提示，原样重发 | 748–750 | 747–749 | 18.78 ms | 194.32 ms | 9.42 ms / 114.94 token/s |

独立预热请求的首段正文耗时 1.56 秒，服务端模型加载耗时 1.46 秒。这条请求单独存档，四组统计只使用模型常驻后的 24 次请求。生成速率按每次请求的服务端生成 token 数除以生成耗时计算，后续并发对照还要按整轮墙钟时间统计总吞吐。

### 同一实例上的并发 1 与 2

沿用短、长提示及生成配置，给每条请求换一个三位数字开头。Ollama 在两个条件下均开两个槽，每槽上下文 2048。预热后做 4 组配对，每种并发每轮提交 2 个短请求和 2 个长请求，组间交替先后顺序。服务日志确认两个槽同时处理过请求，客户端每轮实际峰值在途数为 1 或 2。[并发脚本](../../../practice/local-inference/concurrency_probe.py) · [逐轮逐次结果](../../../practice/local-inference/results/2026-11-23-concurrency.json)

| 客户端并发 | 通过 / 请求 | 首段正文中位数 | 完整回复中位数 | 每轮请求吞吐中位数 | 每轮生成吞吐中位数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 16/16 | 109.72 ms | 286.79 ms | 3.41 请求/s | 68.30 token/s |
| 2 | 16/16 | 194.72 ms | 393.23 ms | 4.92 请求/s | 98.31 token/s |

两组短、长提示分别固定为 51 和 750 token，每条生成 20 token，实际缓存为 3–5 token。并发 2 的整轮生成吞吐约提高 44%，完整回复中位数增加约 37%。分开看，短提示的首段正文中位数从 55.81 ms 增至 134.79 ms，长提示从 158.74 ms 增至 205.44 ms。

### 新服务实例复验

关闭首轮服务后，独立启动三个新实例，逐次核对模型摘要、槽数和模型显存，再跑相同负载。三次新增 96 条正式请求均通过，加上首轮共 128 条。四次运行中，并发 2 的整轮生成吞吐提高 43.60%–44.44%，完整回复中位延迟增加 36.23%–39.48%。每轮原始输出、配置与运行间差异均已归档。[阶段报告](../../../practice/local-inference/stage-report.md)

### 输出长度如何影响并发收益

使用相同模型、GPU 和两个 2048-token 槽。每条提示同时提供短文本和长文本，末尾只切换要逐字复制的目标。短、长输入背景分别实测为 190 和 889 token，在四种条件下总量一致。短输出和长输出分别生成 20 和 117 token，公共前缀实际仅缓存 3–5 token。每个条件跑 4 轮，每轮 2 条短输入和 2 条长输入，轮换测试顺序。64 条正式请求全部通过正文和停止标记验收。[对照脚本](../../../practice/local-inference/output_length_probe.py) · [逐次结果](../../../practice/local-inference/results/2026-11-23-output-length.json)

| 输出长度 | 客户端并发 | 首段正文中位数 | 完整回复中位数 | 整轮生成吞吐中位数 |
| --- | ---: | ---: | ---: | ---: |
| 20 token | 1 | 134.17 ms | 314.41 ms | 61.87 token/s |
| 20 token | 2 | 191.85 ms | 472.56 ms | 81.45 token/s |
| 117 token | 1 | 141.79 ms | 1251.85 ms | 93.52 token/s |
| 117 token | 2 | 254.59 ms | 1463.93 ms | 159.35 token/s |

并发 2 相对并发 1 的吞吐增幅，短输出为 31.66%，长输出为 70.39%。完整回复的中位延迟分别增加 50.30% 和 16.94%。长输出仍多等约 113 ms 才看到首段正文。服务端生成时间占提示处理与生成时间之和的中位比例，从短输出的约 65%–66% 上升至长输出的约 85%–91%。

## 遇到的问题

原计划使用独立 llama.cpp Windows 包和 Qwen3-0.6B GGUF。官方运行包未能及时下载，Hugging Face GGUF 下载连接超时。检查时发现 Ollama 已安装且有 `qwen3:8b` 缓存，因此首日用这套组合完成同一个本机 HTTP 验证。后续性能对照需要固定服务实现、模型和运行配置。

流式对照的预热请求耗时 3.99 秒，服务端报告加载耗时 3.67 秒。后续重复提示都复用了 47 个 token 中的 46 个。单并发基线改用新开头和原样重发来分组，首发仍有 3 个公共模板 token 命中。重发固定发生在首发之后，因此结果适用于紧邻重复请求的场景。

并发阶段固定服务端的两个槽，只改变客户端在途请求上限。前一阶段基线的服务端只有一个槽，并发对照使用本阶段的并发 1 数据作为对照。每次运行每种并发只有 16 条正式请求，四次均在同一台机器上完成，结果适用于当前的短输出混合负载。

为让输出长度对照使用一样长的输入，两个目标文本都加入每条提示。输入因此比前一轮的 51 和 750 token 更长。本次用同一张表里的短输出组衡量相对差异。

## 今日总结

完成普通 HTTP 回复、流式拼接、单并发基线及并发复现。长提示原样重发时首段正文从 171.29 ms 降到 18.78 ms。追加的等长输入对照显示，117 token 输出在两个槽上获得了更大的并发吞吐收益，同时首段正文仍比并发 1 晚到。
