# 2026-11-26：本地推理实作：流量回落后的队列恢复

## 今日目标

**实测结论** — 在本机双槽、连续四批突发后回落到每秒一条的条件下，一条等待与 1 秒放行预算使新请求约 1 秒后恢复持续低等待。延长观察后，无等待队列上限的基线两轮均约 23 秒才达到同一门槛。保护组每轮少完成八条突发请求，且每轮第一条恢复请求仍因队列满被拒绝。

验证连续突发结束后，客户端等待队列何时清空，以及恢复到每秒一条后，新提交的请求何时连续恢复为低等待。沿用昨天的两条在途、一条等待和 1 秒放行预算，增加只限制在途的基线作为对照。[昨日保护策略与预算对照](2026-11-25-local-inference-admission.md)

验收覆盖整轮的唯一终态、等待与在途峰值、放行截止和完整回复。保护组每轮最后四条恢复请求都应完成，且提交到 HTTP 开始不超过 50 ms。基线也用同一门槛做对照。该门槛只用于本次回环复测。

## 核心概念

以恢复段第一条请求的**实际提交**为 `T0`。阶段按预设提交计划标记，排队、HTTP 和终态可以跨过阶段边界。三项时间使用同一个 `T0`。

- **突发等待清空**取 `T0` 时仍在客户端队列中的突发请求最后一次出队的时间，已清空记作 0。出队发生在发放在途名额或等待到期时，原始记录分别保存出队和 HTTP 开始时刻。
- **突发请求结清**取最后一条突发请求到达终态的时间，包含完整回复、到期和立即拒绝。此时恢复段仍可能有在途请求。
- **恢复到低等待**取恢复段末尾连续满足「完整回复且提交到 HTTP 不超过 50 ms」的请求中第一条的提交时间，同时报告这段一共有几条。实际是否完成要等该条请求的最终回复回查。

阶段完成率以该阶段全部提交为分母。提交至 HTTP 和端到端 P90 采用最近秩法，样本为该阶段的完整回复，分别衡量客户端放行前耗时和用户侧完整回复耗时。

## 示例与练习

### 轨迹与复现

沿用 RTX 5070、Ollama `0.40.17` 和 `qwen3:8b`。独立回环实例先预热，日志确认两个服务槽、每槽上下文 2048，客户端最多两条在途。短、长输入保持 190 和 889 token，突发批内按短、长、短、长提交，目标回复为 117 token。每种策略各两轮，第二轮反转次序。

| 阶段 | 计划提交时刻 | 每轮请求数 |
| --- | --- | ---: |
| 平稳 | 0–5 秒，每秒一条 | 6 |
| 突发 | 6、8、10、12 秒，每次四条 | 16 |
| 恢复 | 12.5–19.5 秒，每秒一条 | 8 |

突发间隔由昨天的 3.2 秒压到 2 秒，让连续批次能在基线下积累等待。最后一批后只隔 0.5 秒就提交第一条恢复请求，覆盖保护策略仍可能占用等待名额的过渡段。两种策略共享同一计划轨迹。

在 `practice/local-inference` 下运行。第一条命令复现主实验，第二条只延长恢复段的提交序列。

```powershell
python .\recovery_probe.py --output .\admission-recovery-result.json
python .\recovery_probe.py --recovery-requests 28 --output .\admission-recovery-extended.json
```

第一轮保护组里，`652` 在 `T0` 立即被拒绝，当时等待名额仍被上一批的 `650` 占用。`650` 于 `T0 + 513.75 ms` 到期出队，突发批次最后一条在 `T0 + 1011.25 ms` 完成。下一条恢复请求 `653` 于 `T0 + 1011.30 ms` 提交，7.73 ms 后开始 HTTP，最终完整回复。流量已回落的第一个请求仍可能受到上一批积压影响。

### 延长恢复段定位基线恢复时点

首测中，基线两轮的第八条恢复请求仍分别等了 3.28 和 3.36 秒才开始 HTTP，八条观察窗无法定位基线恢复时刻。补测在新实例保留前 22 条平稳与突发提交，以及同样的两种策略和 50 ms 门槛，只把恢复段从每轮 8 条延长至 28 条，末次计划提交从第 19.5 秒延至第 39.5 秒。

| 策略 | 恢复段完成 / 提交 | 突发等待清空 | 突发请求结清 | 客户端等待最后出队 | 连续低等待起点与条数 |
| --- | ---: | ---: | ---: | ---: | --- |
| 基线 | 56/56 | 4.58–4.62 秒 | 6.09–6.16 秒 | 22.07–22.10 秒 | 23.00–23.01 秒，两轮各 5 条 |
| 保护组 | 54/56 | 0.51 秒 | 1.01–1.02 秒 | 0.51 秒 | 1.00–1.01 秒，两轮各 27 条 |

表中时间均从 `T0` 起算，范围来自两轮。客户端等待最后出队按整轮所有请求的 `queue_exit_ms` 取最大值，包含恢复段入队的请求。基线的突发请求约在 `T0 + 6 秒` 结清，恢复段请求最后一次出队约在 `T0 + 22.1 秒`。第 23 条恢复请求在两轮中分别耗时 112.45 和 85.59 ms 才开始 HTTP，随后连续五条都在 6 ms 内开始 HTTP 并完整回复。[延长观察逐条记录](../../../practice/local-inference/results/2026-11-26-admission-recovery-extended.json)

延长观察的保护组仍是每轮第一条恢复请求队列满，随后 27 条全部完成。第一轮第二条恢复请求 `673` 在 `T0 + 1010.65 ms` 开始 HTTP，最后一条突发请求在 `T0 + 1016.91 ms` 才完成。空出的一个名额已足以开始接收新请求，因此低等待可以先于突发请求全部结清。

## 遇到的问题

延长观察中的基线完成了 56/56 条恢复请求，每轮前 23 条的提交至 HTTP 耗时都超过 50 ms。保护组的成功回复 P90 统计了完整回复，另用终态计数记录每轮第一条立即拒绝。复盘同时保留阶段完成率、等待队列状态和恢复起点。八条观察段中基线未达到门槛，延长后的恢复时点也只能定位到约 1 秒的提交采样间隔。

两次运行都使用固定输入和输出、无重试的回环流量以及本机双槽。1 秒预算的约束范围截止于 HTTP 开始。

## 今日总结

主实验和补测共验收 320 条提交，284 条完整回复、12 条放行前超时、24 条队列满拒绝。每条均有唯一终态，36 条未放行记录的 HTTP 开始时间均为空，无请求错误。两次运行的保护组四轮都满足末尾四条低等待的验收线，每轮在第二条恢复请求开始进入连续低等待。基线用较长等待完成了全部请求，保护策略以丢弃部分突发请求和第一条恢复请求为代价，缩短了后来请求受积压影响的时间。
